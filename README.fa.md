# PQTunnel — نسخهٔ آزمایشی

**نسخه: 0.3.0-dev · وضعیت: نمونهٔ اولیه؛ آمادهٔ استفادهٔ تولیدی نیست.**

PQTunnel یک تونل آزمایشی لایهٔ ۳ با encapsulation بسته‌های IPv4 و IPv6 است که TCP را داخل TLS 1.3 حمل می‌کند و برای تبادل کلید، گروه هیبریدی `X25519MLKEM768` را به‌صورت اجباری انتخاب می‌کند. احراز هویت با گواهی‌های دوطرفه و CA خصوصی انجام می‌شود.

> **هشدار امنیتی:** این پروژه audit امنیتی مستقل نشده است. آن را برای فعالیت حساس یا روی سرور عملیاتی استفاده نکن. تبادل کلید پساکوانتومی/هیبریدی است، اما امضای گواهی‌ها فعلاً Ed25519 کلاسیک است؛ بنابراین کل سامانه پساکوانتومی نیست. هیچ رمزنگاری‌ای تضمین ابدی «غیرقابل‌شکستن» ندارد.

## چه چیزهایی اضافه یا بهبود یافته‌اند؟

- حمل بسته‌های IPv4 و IPv6 و فیلتر route بر پایهٔ CIDR برای لینک آزمایشی server-to-server؛ تنظیم واقعی مسیرهای IPv6 هنوز دستی و آزمایش‌نشده است.
- فیلتر پورت مقصد TCP/UDP با `--allowed-dst-ports`، مثل `tcp:443,udp:53,tcp:8000-8010`؛ با فعال‌بودن فیلتر، بسته‌های fragment‌شده عمداً رد می‌شوند.
- helper آزمایشی `scripts/site-to-site-selective.sh` برای policy routing انتخابی روی پورت‌های خروجی و DNAT/SNAT پورت‌های ورودی؛ نیازمند میزبان آزمایشی اختصاصی و بررسی دستی است.
- پارامترهای transport برای hostname/IPv4/IPv6 (`--server`, `--server-name`, `--network tcp|tcp4|tcp6`) و حالت peer-prefix تک‌اتصالی.
- مسیر نصب سرویس Ubuntu با systemd در `scripts/install-server.sh` و `deploy/systemd/pqtunneld.service`.
- اسکریپت مستقل و قابل بازگردانی برای فعال‌سازی IPv4 forwarding و NAT در `scripts/server-network.sh`؛ فقط جدول اختصاصی nftables خودش را مدیریت می‌کند و UFW را تغییر نمی‌دهد.
- اسکریپت شبکهٔ کلاینت لینوکس در `scripts/linux-client-network.sh`: route اختصاصی IP سرور، مسیر پیش‌فرض IPv4 از TUN، DNS با systemd-resolved و blackhole برای مسیر پیش‌فرض IPv6.
- محدودسازی تعداد نشست‌ها و handshakeهای هم‌زمان در سرور.
- گردش‌کار CI برای تست و cross-build لینوکس و ویندوز و ساخت فایل‌های Release از روی تگ نسخه.
- اصلاح مسیر ماژول Go به `github.com/hatinati2/PQTunnel`.

## محدودیت‌ها را جدی بگیر

1. اسکریپت شبکهٔ سرور UFW، فایروال ارائه‌دهنده، باز کردن پورت TCP و قواعد موجود دیگر را تغییر نمی‌دهد. در صورت فعال بودن UFW ممکن است فوروارد همچنان مسدود باشد.
2. اسکریپت کلاینت لینوکس یک kill-switch ممیزی‌شده و ماندگار نیست. هنگام اجرای تنظیمات، مسیر IPv4 به TUN می‌ماند و مسیر پیش‌فرض IPv6 مسدود می‌شود؛ ولی تنظیمات در reboot ماندگار نیستند و مسیرهای دستی/برنامه‌هایی که به رابط فیزیکی bind می‌شوند نیاز به سیاست فایروال جدا دارند.
3. ویندوز به درایور/ DLL رسمی Wintun و آداپتور ازپیش‌ساخته‌شدهٔ `pqtun0` نیاز دارد؛ مدیریت کامل route، DNS و kill-switch ویندوز هنوز در پروژه نیست.
4. اپ اندروید فقط شالوده است؛ AAR باید با `gomobile` ساخته شود، واردکردن گواهی‌ها از رابط کاربری پیاده نشده و اپ روی دستگاه واقعی آزمایش نشده است.
5. انتقال از یک جریان TCP استفاده می‌کند و ممکن است دچار TCP-over-TCP و تأخیر head-of-line شود.
6. ابطال برخط گواهی، تحویل امن خودکار تنظیمات دستگاه و امضای کاملاً پساکوانتومی گواهی‌ها وجود ندارد.

## پیش‌نیازها

- Go نسخهٔ 1.24 یا بالاتر؛ CI از Go 1.27.x استفاده می‌کند. پشتیبانی TLS از `X25519MLKEM768` از Go 1.24 اضافه شد. [یادداشت انتشار رسمی Go 1.24](https://go.dev/doc/go1.24)
- سرور Ubuntu/Linux دارای systemd، `iproute2`، `nftables` و `/dev/net/tun`.
- کلاینت لینوکس دارای `iproute2` و `systemd-resolved` (برنامهٔ `resolvectl`).
- ویندوز: درایور/DLL رسمی Wintun و آداپتور از قبل آماده‌شده با نام `pqtun0`؛ این پروژه درایور را توزیع نمی‌کند.
- اندروید: Android Studio/SDK/NDK و `gomobile`.

## ساخت و تست

```sh
go test ./...
go vet ./...
go build ./cmd/pqtunneld ./cmd/pqtunnel-client ./cmd/pqtunnel-pki
```

CI تست‌ها و cross-build برای Linux amd64/arm64 و Windows amd64 انجام می‌دهد؛ همچنین روی Ubuntu 24.04 و 26.04 تونل TUN واقعی، پورت‌فوروارد ورودی TCP/UDP و خروج انتخابی TCP/443 و UDP/53 در برابر ترافیک مستقیم TCP/8080 و UDP/5353 را برای IPv4 و IPv6 داخل network namespaceهای ایزوله آزمایش می‌کند. این تست‌ها فایروال ارائه‌دهنده یا کارکرد روی دو VPS واقعی را تأیید نمی‌کنند. ساخت Android هنوز در CI تأیید نمی‌شود.

## ساخت گواهی‌ها

این دستورات برای محیط توسعهٔ مورد اعتماد هستند؛ آن‌ها را در محیط امن اجرا کن، نه روی سرور عمومی:

```sh
go run ./cmd/pqtunnel-pki init --out ./pki --server-name vpn.example.com
go run ./cmd/pqtunnel-pki issue-client --out ./pki --ip 10.66.0.2
```

برای هر دستگاه یک IP یکتا صادر کن. فایل `ca.key` باید آفلاین/خصوصی بماند و **نباید** به سرور یا کلاینت منتقل شود. سرور فقط به `server.crt`، `server.key` و `ca.crt` نیاز دارد. هر کلاینت باید `ca.crt` و گواهی/کلید خصوصی اختصاصی خودش را دریافت کند. کلید خصوصی را از کانال امن جداگانه انتقال بده.

امضای گواهی‌ها فعلاً Ed25519 کلاسیک است؛ پس `X25519MLKEM768` به معنی پساکوانتومی‌بودن کامل احراز هویت نیست. در حالت server-to-server تک‌peer، هر دو مقدار `PQTUNNEL_PEER_PREFIXES` (CIDRهای مجاز مبدأ peer و مسیر برگشت) و `PQTUNNEL_LOCAL_PREFIXES` (CIDRهای مقصد مجاز سمت Listener) را در `/etc/default/pqtunneld` تنظیم کن، `PQTUNNEL_PEER_NAME` را مشخص کن و `PQTUNNEL_MAX_CLIENTS=1` قرار بده؛ نام peer باید دقیقاً با Common Name گواهی صادرشده برابر باشد. Listener certificate paths can be selected with `PQTUNNEL_TLS_CERT` and `PQTUNNEL_TLS_KEY` when reversing roles.

## بسته‌بندی سرور Ubuntu

فایل‌های نصب از تغییرات شبکه جدا شده‌اند تا نصب سرویس، بی‌سروصدا قواعد NAT یا فایروال را عوض نکند.

1. پوشهٔ PKI سرور باید شامل `server.crt`، `server.key` و `ca.crt` باشد؛ `ca.key` را روی سرور قرار نده. نصب‌کننده زنجیرهٔ گواهی سرور و مطابقت کلید خصوصی با گواهی را بررسی می‌کند.
2. فایل‌های `scripts/install-server.sh` و `deploy/systemd/pqtunneld.service` را بازبینی کن. نصب‌کننده هم سورس کامل (با Go 1.24+) و هم بستهٔ Release لینوکس دارای باینری آمادهٔ `pqtunneld` را می‌پذیرد. اگر نصب قبلی پیدا کند، از بازنویسی آن خودداری می‌کند. به‌صورت پیش‌فرض سرویس را اجرا/فعال نمی‌کند؛ `--enable` آن را فعال و اجرا می‌کند. این اسکریپت ابزار ارتقا نیست.
3. `scripts/server-network.sh` فقط برای میزبان آزمایشی اختصاصی طراحی شده است. اگر IPv4 forwarding از قبل فعال باشد، UFW فعال باشد یا قوانین nftables/iptables موجود باشند، از اعمال تغییر خودداری می‌کند. زنجیرهٔ forward آن سیاست `drop` دارد و فقط ترافیک بین `pqtun0` و رابط خروجی مشخص‌شده را برای زیرشبکهٔ کلاینت‌ها مجاز می‌کند؛ سایر ترافیک‌های IPv4 فورواردشده مسدود می‌شوند. آن را بدون بازبینی اختصاصی روی روتر، سرور دارای تونل‌های فعال یا VPS عملیاتی اجرا نکن.
4. این ابزار پورت TCP 8443 را در فایروال میزبان یا ارائه‌دهنده باز نمی‌کند. ادغام با فایروال، ازجمله UFW، باید جداگانه بررسی شود.

اسکریپت نصب یا شبکه را روی میزبان راه‌دور بدون کنسول یا مسیر بازیابی خارج از باند اجرا نکن. این اسکریپت‌ها روی سرور فعلی، تونل‌های فعال، فایروال ارائه‌دهنده یا مسیرهای موجود تو آزمایش نشده‌اند. تا پیش از بازبینی و آزمون در محیط آزمایشگاهی، روی VPS فعلی نصب نکن.

## آماده‌سازی شبکهٔ کلاینت Linux

از `scripts/client.env.example` یک کپی در `/etc/pqtunnel/client.env` بساز، IP سرور را به‌صورت **IPv4 عددی و ثابت** وارد کن، IP تونل یکتایی انتخاب کن و ابتدا `scripts/linux-client-network.sh` را بازبینی کن.

- `up` پیش از تغییر مسیر پیش‌فرض، مسیر فیزیکی جداگانه‌ای برای IP سرور ثبت می‌کند؛ سپس IPv4 را از TUN عبور می‌دهد، دامنهٔ پیش‌فرض DNS را به رابط TUN هدایت و مسیر پیش‌فرض IPv6 را در صورت وجود blackhole می‌کند.
- بعد، `pqtunnel-client` را با همان IP سرور، نام TLS، گواهی، کلید و IP محلی اجرا کن.
- پیش از اجرای `down`، فرایند کلاینت را متوقف کن. `down` عمداً اینترنت عادی را بازمی‌گرداند.

این ابزار هنوز kill-switch قابل‌ممیزی و ماندگار نیست؛ تغییر مسیرها در راه‌اندازی مجدد سیستم باقی نمی‌ماند و پیش از اعمال تنظیمات هنگام boot، احتمال نشت وجود دارد. ابتدا روی دستگاه آزمایشی و بدون ترافیک حساس تست کن.

## ویندوز و Android

در ویندوز، آداپتور `pqtun0` باید از قبل در دسترس باشد؛ مدیریت کامل مسیرهای ویندوز، DNS و kill-switch هنوز آماده نیست. به [پروژهٔ رسمی Wintun](https://git.zx2c4.com/wintun) مراجعه کن.

برای Android، فرمان `make android-aar` در Makefile اضافه شده است؛ ابتدا `gomobile` و Android SDK/NDK را آماده کن. فایل‌های `ca.crt`، `client.crt` و `client.key` در پوشهٔ خصوصی `files/pki` اپ قرار می‌گیرند؛ روش ورود گواهی از UI هنوز وجود ندارد. هیچ کلید یا گواهی محرمانه را commit نکن.

## انتشار نسخه

ساخت تگ نسخه با پیشوند `v`، workflow فایل `.github/workflows/release.yml` را اجرا می‌کند تا باینری‌های Linux amd64/arm64 و Windows amd64 تولید شوند. ساخت Release به معنی آماده‌بودن VPN برای استفادهٔ تولیدی نیست.
