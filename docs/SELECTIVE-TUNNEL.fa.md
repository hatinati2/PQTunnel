# راهنمای آزمایشی تونل انتخابی PQTunnel

**وضعیت: توسعه‌ای و آزمایش‌نشده روی دو VPS واقعی.** این سند طراحی دو قابلیت را توضیح می‌دهد: (۱) عبور ترافیک خروجیِ خود سرور ایران بر اساس پورت مقصد؛ (۲) نگاشت پورت ورودی ایران به مقصدی در سمت آلمان. فعلاً این مسیر برای حالت «ایران = Dialer، آلمان = Gateway/Listener» طراحی شده است. شروع اتصال از آلمان، درحالی‌که خروجی همچنان از آلمان باشد، هنوز پیاده‌سازی و آزمون نشده است؛ جابه‌جایی سادهٔ نقش‌های client/server معادل reverse transport کامل نیست.

## ۱. قانون پورت در خود برنامه

کلاینت و Listener هر دو گزینهٔ `--allowed-dst-ports` و متغیر محیطی `PQTUNNEL_ALLOWED_DST_PORTS` دارند. فرمت CSV:

```text
tcp:443,udp:53,udp:123,tcp:8000-8010
```

هر قانون پروتکل و پورت مقصد را مشخص می‌کند. اگر فهرست خالی باشد، فیلتر پورت برنامه خاموش است؛ برای سرور عمومی/آزمایشی سایت‌به‌سایت، فهرست یکسان و حداقلی را روی کلاینت و سرور تنظیم کنید. پورت‌های مقصدِ نگاشت‌شده در قواعد port-forward نیز باید در این فهرست باشند؛ مثلاً اگر `8443` ایران به `203.0.113.50:443` می‌رود، فهرست باید `tcp:443` را شامل شود، نه صرفاً `tcp:8443`.

این فیلتر برای جلوگیری از ابهام، بسته‌های fragmented را رد می‌کند. IPv6 extension headers متداول پیمایش می‌شوند، اما fragment header و پروتکل‌های غیر TCP/UDP با فعال‌بودن allowlist عبور نمی‌کنند. در نتیجه این مرحله جایگزین فایروال کامل سیستم‌عامل نیست.

## ۲. ترافیک خروجی انتخابی از ایران به آلمان

اسکریپت `scripts/site-to-site-selective.sh` از `nftables` و `ip rule/fwmark` استفاده می‌کند تا **ترافیک تولیدشده روی خود میزبان ایران** که پورت مقصد TCP/UDP آن در فهرست است، به رابط `pqtun0` هدایت شود. سایر پورت‌های TCP/UDP و سایر پروتکل‌ها از این قاعده انتخابی پیروی نمی‌کنند.

نمونهٔ تنظیم برای سرور Dialer ایران در `scripts/site-to-site.env.example` آمده است. `PQTUNNEL_TCP_EGRESS_PORTS=443` و `PQTUNNEL_UDP_EGRESS_PORTS=53,123` فقط مثال هستند؛ پورت‌های خودت را جایگزین کن. جدول‌های policy routing از شماره‌های اختصاصی 518 و 519 استفاده می‌کنند و markهای 20560/20561/20562 را رزرو می‌کنند.

برای جلوگیری از اینکه جریان TLS خود PQTunnel به‌خاطر پورت مقصد وارد تونل خودش شود، اجرای Linux client باید از `--socket-mark 20560` استفاده کند. این گزینه روی Linux از `SO_MARK` استفاده می‌کند و به مجوز مناسب شبکه نیاز دارد.

**محدودیت دامنه:** اگر UDP/53 را برای خروج انتخاب کرده‌ای، در اولین اتصال از IP عددی سرور آلمان در `--server` استفاده کن و دامنه را در `--server-name` نگه دار تا اعتبارسنجی نام TLS انجام شود. این کار از وابستگی bootstrap DNS به تونلی که هنوز وصل نشده جلوگیری می‌کند. پشتیبانی از دامنه برای endpoint TLS جدا از حل DNS امن و پویای targetهای NAT است.

## ۳. انتقال پورت ورودی از ایران به آلمان

برای هر mapping یک قانون TCP یا UDP با فرمت زیر تعیین می‌شود:

```text
localPort=targetIP:targetPort
```

برای IPv6:

```text
localPort=[2001:db8::50]:targetPort
```

نمونه: `PQTUNNEL_TCP_FORWARD_RULES=8443=203.0.113.50:443` یعنی اتصال ورودی به پورت TCP/8443 سرور ایران با DNAT/SNAT از تونل عبور می‌کند و به آدرس مقصد/پورت 443 می‌رسد. آدرس target باید IP literal باشد؛ نام دامنه برای مقصد DNAT در این نسخه resolve و به‌صورت پویا به‌روزرسانی نمی‌شود.

برای این روش، سرویس سمت آلمان باید در IP/پورت هدف قابل‌دسترسی باشد. به‌دلیل SNAT، سرویس مقصد مبدأ اتصال را به‌شکل آدرس تونل ایران (`10.66.0.2` یا `fd42:7061:7475::2`) می‌بیند، نه IP واقعی کاربر نهایی. حفظ IP واقعی کاربر در این نسخه پیاده‌سازی نشده است.

## ۴. تنظیم نقش‌ها و فهرست مجاز

- ایران: Dialer و محل اعمال قانون‌های `*_EGRESS_PORTS` و `*_FORWARD_RULES`.
- آلمان: Gateway/Listener، با خروجی NAT از رابط WAN.
- هر دو سمت باید از CA مورداعتماد و گواهی‌های mTLS استفاده کنند. `ca.key` روی هیچ‌کدام از VPSها قرار نمی‌گیرد.
- در `/etc/default/pqtunneld` سمت آلمان، `PQTUNNEL_PEER_PREFIXES` باید حداقل آدرس overlay ایران را شامل کند (`10.66.0.2/32,fd42:7061:7475::2/128`)، `PQTUNNEL_LOCAL_PREFIXES` باید مقصدهای مجاز را شامل کند، `PQTUNNEL_PEER_NAME` باید با هویت گواهی peer یکی باشد، و `PQTUNNEL_MAX_CLIENTS=1` باقی بماند.
- `PQTUNNEL_ALLOWED_DST_PORTS` در Listener باید اتحادیهٔ پورت‌های مقصد انتخاب‌شده و پورت‌های target در forwarding باشد، مانند `tcp:443,udp:53,udp:123` برای مثال ساده بالا.
- رابط TUN سمت Gateway از IPv4 `10.66.0.1/24` استفاده می‌کند و اسکریپت Gateway آدرس overlay IPv6 `fd42:7061:7475::1/64` را اضافه می‌کند. ایران از `10.66.0.2/24` و `fd42:7061:7475::2/64` استفاده می‌کند.

## ۵. اسکریپت شبکه و شروط ایمنی

اسکریپت جدید در `scripts/site-to-site-selective.sh` این عمل‌ها را دارد:

- `validate`: فقط تنظیمات را می‌خواند و اعتبارسنجی می‌کند.
- `preview`: فقط فایل احتمالی nftables را چاپ می‌کند؛ چیزی را اعمال نمی‌کند.
- `status`: وضعیت فعلی rule/tableها را می‌خواند.
- `dialer-up` و `gateway-up`: عملیات تغییردهندهٔ شبکه هستند.
- `dialer-down` و `gateway-down`: تلاش برای rollback عملیات همین اسکریپت هستند.

این helper روی میزبان اختصاصی آزمایش طراحی شده و اگر UFW فعال، قواعد قبلی nftables/iptables، policy-routing ruleهای هم‌شماره، TUN مدیریت‌نشده یا forwarding از قبل فعال باشد، باید از اعمال تغییر خودداری کند. زنجیرهٔ forward آن `policy drop` دارد و روی یک روتر یا میزبان عملیاتی می‌تواند ترافیک فورواردی دیگر را مسدود کند. `gateway-down` نیز تا وقتی `pqtunneld` فعال باشد از rollback خودداری می‌کند. این رفتارها عمدی‌اند تا به‌جای تغییر خودکار فایروال موجود، fail-closed باشد.

برای استفادهٔ بعدی، ابتدا فقط `bash scripts/site-to-site-selective.sh validate` و `bash scripts/site-to-site-selective.sh preview` را در محیط آزمایش اجرا و قواعد تولیدشده را بازبینی کن. هنوز اجرای `dialer-up`/`gateway-up` روی VPS فعلی توصیه نمی‌شود؛ صحت نحو nftables باید با `nft -c` روی Ubuntu واقعی، مسیر برگشت، NAT، DNS، IPv6 و عملکرد انتها‌به‌انتها باید روی دو میزبان آزمایشی و با دسترسی console/out-of-band بررسی شود. عملیات `*-up` و `*-down` تغییردهنده‌اند؛ تا بازبینی نهایی آن‌ها را روی سرور عملیاتی اجرا نکن.

## ۶. وضعیت فعلی

این milestone فیلتر پروتکل/پورت در لایهٔ برنامه و تولید سیاست شبکهٔ انتخابی را اضافه می‌کند، اما کد هنوز audit امنیتی نشده و روی Ubuntu واقعی با دو VPS آزمایش نشده است. mode معکوس واقعی، حفظ IP واقعی بازدیدکننده برای port-forward، resolve پویای domain برای DNAT، rules پایدار بعد از reboot، و آزمون end-to-end TCP/UDP در شبکهٔ واقعی هنوز باقی‌اند.
