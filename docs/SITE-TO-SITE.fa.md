# راهنمای آزمایشی تونل سرور‌به‌سرور PQTunnel

**این راهنما معماری و پارامترهای برنامه را توضیح می‌دهد؛ به معنی آماده بودن نصب روی VPS عملیاتی نیست.** هیچ‌یک از تنظیمات مسیر، forwarding، فایروال یا NAT خودکار با اجرای برنامه انجام نمی‌شود.

## نسخه‌های سیستم‌عامل

نقش برنامه از نسخهٔ Ubuntu مستقل است. تمام چهار ترکیب Ubuntu 24.04 و 26.04 باید آزمایش شوند:

| Listener | Dialer |
|---|---|
| Ubuntu 24.04 | Ubuntu 24.04 | نیازمند آزمون انتها‌به‌انتها |
| Ubuntu 24.04 | Ubuntu 26.04 | نیازمند آزمون انتها‌به‌انتها |
| Ubuntu 26.04 | Ubuntu 24.04 | نیازمند آزمون انتها‌به‌انتها |
| Ubuntu 26.04 | Ubuntu 26.04 | نیازمند آزمون انتها‌به‌انتها |

CI علاوه بر build و unit test، `scripts/test-site-to-site-netns.sh` را با رابط TUN واقعی و ping دوطرفهٔ IPv4/IPv6 اجرا می‌کند؛ `scripts/test-selective-forward-netns.sh` نیز رفت‌وبرگشت واقعی پورت‌فوروارد ورودی TCP و UDP را روی هر دو خانوادهٔ IPv4 و IPv6 در network namespaceهای دورریختنی می‌سنجد. این تست‌ها جای چهار ترکیب Ubuntu یا ارتباط بین دو VPS مجزا را نمی‌گیرند.

## مستقیم و ریورس

در پروتکل، یک سمت **Listener** است و سمت دیگر **Dialer**. برای تونل ایران به خارج، اگر سرور ایران اتصال خروجی TCP به خارج را آغاز کند، معمولاً سرور خارج Listener و سرور ایران Dialer قرار می‌گیرد. **توجه:** نسخهٔ فعلی برای سناریوی موردنظر این پروژه، ایران به‌عنوان Dialer و آلمان به‌عنوان Gateway/Listener را هدف می‌گیرد. تغییر سادهٔ نقش client/server، حالت reverse-initiated را درحالی‌که خروجی همچنان از آلمان باشد، کامل پیاده‌سازی نمی‌کند؛ این حالت هنوز نیازمند طراحی و آزمون جداگانه است.

Listener می‌تواند با یک آدرس یا فهرست comma-separated مانند `0.0.0.0:8443,[::]:8443` روی IPv4 و IPv6 گوش کند؛ مقدار `PQTUNNEL_LISTEN` در فایل محیط systemd باید با دسترسی واقعی IPv6 میزبان هماهنگ باشد؛ در صورت نبود IPv6 روی میزبان، listener مربوط به IPv6 را جداگانه حذف کن. هر دو طرف می‌توانند از آدرس endpoint به شکل دامنه، IPv4 یا IPv6 استفاده کنند. در کلاینت، `--server` آدرس انتقال است و باید با پورت مشخص شود؛ IPv6 literal در آدرس TCP باید داخل براکت باشد. `--server-name` نام دامنه یا IP موجود در SAN گواهی TLS است و مستقل از آدرس انتقال است. `--network tcp`, `tcp4` یا `tcp6` امکان انتخاب خانوادهٔ انتقال را می‌دهد.

## Prefixها و سیاست بسته

در حالت server-to-server، Listener در حالت site-to-site دو allowlist مجزا می‌گیرد: `--peer-prefixes` برای sourceهای مجاز و route برگشتی به سمت Dialer؛ `--local-prefixes` برای مقصدهای مجاز در سمت Listener. هر دو باید CIDRهای دقیق باشند. در مسیر خروجی از TUN سرور به سمت تونل، مبدأ بسته هم باید عضو `--local-prefixes` باشد؛ صرفاً داشتن مقصد در routeهای peer کافی نیست. Dialer نیز مبدأ محلی و مقصد سمت مقابل را کنترل می‌کند، پس CIDRها را فقط به‌اندازهٔ شبکه‌های واقعی باز کن. برای جلوگیری از route مبهم، این حالت فعلاً با **یک peer فعال** و `--max-clients=1` پشتیبانی می‌شود. `--peer-name` نیز باید دقیقاً با Common Name گواهی Peer برابر باشد تا گواهی دیگری از همان CA نتواند prefixها را تصاحب کند.

Dialer باید هم `--local-prefixes` و هم `--remote-prefixes` را تعیین کند:

- `--local-prefixes`: آدرس TUN و/یا subnetهای محلی که اجازهٔ حضور در بسته‌های ارسالی/دریافتی دارند.
- `--remote-prefixes`: subnetهای قابل‌دسترسی در سمت Listener. در full-tunnel می‌توان default prefixهای IPv4 و IPv6 را تعریف کرد، اما فقط پس از طراحی مسیرهای underlay و سیاست fail-closed.

برای site-to-site معمولی، از CIDRهای دقیق LAN استفاده کن و از default route فقط با برنامهٔ بازیابی خارج از باند استفاده کن. زیرشبکه‌های دو طرف نباید با هم overlap داشته باشند.

## دامنه، IPv4 و IPv6

- DNS دامنه باید پیش از اعمال routeهای تونل قابل resolve باشد؛ route اختصاصی به IPهای resolvedشدهٔ endpoint باید حفظ شود تا اتصال TLS از داخل همان تونل loop نشود.
- IPv4 و IPv6 هر دو در framing و فیلتر prefix پروتکل پشتیبانی می‌شوند. IPv6 jumbogram پشتیبانی نمی‌شود.
- پشتیبانی IPv6 در transport به معنی قابل‌دسترس بودن IPv6 در هر دو VPS نیست. همچنین encapsulation بستهٔ IPv6 به‌تنهایی route، forwarding، firewall یا NAT64/NAT66 را تنظیم نمی‌کند.
- اسکریپت `server-network.sh` فعلی تنها IPv4 forwarding/NAT را مدیریت می‌کند و برای فایروال یا IPv6 طراحی نشده است.

## TLS و گواهی‌ها

- از TLS 1.3 با گروه هیبریدی `X25519MLKEM768` استفاده می‌شود و fallback کلاسیک عمداً وجود ندارد.
- امضای گواهی‌ها فعلاً Ed25519 کلاسیک است؛ پس کل سامانه «کاملاً پساکوانتومی» نیست.
- کلید `ca.key` باید آفلاین یا در محیط کاملاً مورداعتماد بماند و هرگز به دو سرور منتقل نشود.
- برای هر hostname/IP که قرار است Listener باشد، گواهی Server با همان SAN لازم است. هر Dialer نیز گواهی Peer جداگانه می‌گیرد.

## وضعیت فعلی

کد پروتکل IPv4/IPv6 و allowlist پیشوندها پیاده‌سازی شده است. CI مسیر واقعی TUN/route، رفت‌وبرگشت پورت‌فوروارد ورودی TCP/UDP و خروج انتخابی چندپورتی را داخل namespaceهای جداگانه آزمایش می‌کند: TCP/443 و TCP/8443 و UDP/53 و UDP/5354 از تونل عبور می‌کنند؛ پورت‌های غیرمجاز و پروتکل اشتباه روی TCP/53 یا UDP/443 مستقیم می‌مانند. این ماتریس برای IPv4 و IPv6 اجرا می‌شود، اما سیاست‌های دلخواه دیگر یا helper شبکهٔ site-to-site را روی دو VPS واقعی تأیید نمی‌کند؛ فایروال ارائه‌دهنده و یکپارچگی با قواعد NAT/فایروال موجود همچنان نیازمند آزمون جداگانه‌اند. این نسخه همچنان فقط برای محیط آزمایشی با مسیر بازیابی مستقل مناسب است.

## عبور انتخابی پورت‌ها

برای هدایت فقط بعضی پورت‌های TCP/UDP و نگاشت پورت ورودی از ایران به آلمان، فایل [راهنمای تونل انتخابی](SELECTIVE-TUNNEL.fa.md) را ببین. این قواعد از `nftables`/`ip rule` استفاده می‌کنند و هنوز روی دو VPS واقعی تست نشده‌اند.
